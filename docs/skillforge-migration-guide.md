## 0. 为什么要单独写这份指南

FR-48 解决的是"**接管时不产生 Git diff**"这个技术问题。但用户真正遇到的是另一个问题：

> 「我们团队已经用 `.cursorrules` 共享规范两年了，现在要切到 SkillForge，**这份文件怎么办？规范怎么变成 skill？同事怎么跟上？**」

这不是一个技术开关能回答的，它是一段**有状态、有中间态、需要全员协调**的迁移过程。本指南就是这段过程的剧本。

> ⚠ **本指南同时是 FR-48 的需求探测器**：第 6 节列出了迁移中会踩到、但 FR-48 当前设计**尚未覆盖**的六个场景。这些应当在 M1 实现前回到 PRD 与架构文档确认。

## 1. 迁移前：先做资产盘点（不要跳过）

| # | 盘点项 | 为什么必须先做 |
| --- | --- | --- |
| 1 | 团队仓库里**存在哪些** AI 规则文件？全路径列出（注意不只在根目录） | 见 §6.3，`.github/copilot-instructions.md` 这类**不在根目录** |
| 2 | 每个文件**是否被 Git 跟踪**？（`git ls-files`） | 决定走 FR-46（新建隔离）还是 FR-48（存量接管） |
| 3 | 每个文件**是否仍在被维护**？最近一次修改时间 | 僵尸文件可直接弃用，无需迁移 |
| 4 | 文件里**哪些内容是"规则"、哪些是"项目说明"**？ | 见 §2.1，只有"规则"该转成 skill |
| 5 | 团队里**谁在维护**这份文件？ | 迁移需要这个人参与，否则规范语义会失真 |

> **产出物**：一张盘点表。这张表同时是 FR-48「候选文件名冲突检测」的人工输入。

## 2. 核心决策：整体转一个 skill，还是按主题拆多个？

### 2.1 建议：**按主题拆多个**（强烈建议，不作为可选项）

理由四条，按重要性排序：

| # | 理由 | 不拆的代价 |
| --- | --- | --- |
| 1 | **上下文成本**。skill 的价值在于"按需加载"。一个 3000 字的规范文件整体加载，每次对话都吃掉固定上下文；拆成 8 个主题后，每次只加载相关的 1~2 个 | 每次对话都在为用不到的规则付费 |
| 2 | **准确率可度量**。一个巨大的 skill，采纳率是所有主题的平均值——**看不出哪部分不好用**，也就无从优化（§6.4 SkillScore 失去意义） | 无法定位问题，FR-22 看板退化为一个不可行动的平均值 |
| 3 | **触发词精度**。整体一个大 skill 的触发词必然宽泛（"代码""规范"），导致**误命中率高**；拆分后每个主题有精准触发词（"错误码""枚举命名"） | G1-A（Top1 采纳率 ≥70%）大概率达不到 |
| 4 | **演进粒度**。某个主题更新不影响其他主题的版本与采纳历史 | 改一条规则就要整体升版本，历史数据被稀释 |

### 2.2 拆分粒度的判断标准（给执行者）

**一个 skill ≈ 一个"能被一句话描述清楚的规则簇"。**

- ✅ **可成独立 skill**：标题能被写成「当 **X** 时应该 **Y**」的形式。例：「新增 RPC 接口时的命名与错误码规范」
- ❌ **不成 skill**：纯说明性内容（项目背景、术语表、目录结构说明、负责人名单）——**留在 README / `docs/`，不迁移**
- 📏 **体量上限**：单个 skill 正文建议 **≤ 200 行**。超过就该拆

### 2.3 拆分后每个 skill 必须补齐的元数据（FR-02 / FR-04）

| 字段 | 要求 | 常见坑 |
| --- | --- | --- |
| `name` | 短、唯一、slug 友好 | 从原文件章节标题直接照搬往往过长 |
| `summary` | **必填**，一句话（Tier B/C 下要进路由索引，两处复用） | 原文件通常没有摘要，需人工补 |
| `triggers` | 3~5 个触发关键词 | 这是新增信息，原文件里没有——**必须由熟悉该规范的人补**，不能靠猜 |
| `tags` | 分类标签 | — |

> **⚠ 这是迁移中最大的人工成本项**，且**不能自动化**：触发词体现了"什么情况下该用这条规范"，只有维护者知道。应预估每个 skill 约 10~15 分钟人工整理时间。

## 3. 转换后：原文件怎么处理？

### 3.1 三种处置方案（含一个反直觉的结论）

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **删除** | 拆成 skill 后删除原文件 | 终态最干净，但**必须全员同步**（见 §3.3），否则有人丢失规则 |
| **共存**（⚠ 有陷阱） | 保留原文件，同时启用 skill | **不推荐长期共存**。理由见 §3.2 |
| **降级为人类文档** | 把原文件**移到 Metis 不会自动读取的位置**（如 `docs/coding-standards.md`）或改名，保留其**人类可读性** | ✅ **推荐的过渡态**：人类仍能查规范全文，但 AI 不再重复加载它 |

### 3.2 ⚠ 反直觉结论：「保留原文件」不是无害选项

很多人会本能地选"保留原文件，反正多一份没关系"。**这是错的**：

1. **规则被加载两次**，上下文成本翻倍——原文件常驻上下文，skill 又被注入一遍
2. **两份内容会漂移**：skill 改了、原文件没改（或反之），Metis 收到**互相冲突**的两套指令，行为不可预测
3. **无法归因**：出现问题时，不知道是原文件的规则还是 skill 的规则生效了，准确率数据失去意义

> **结论**：共存只能是**短过渡态**（建议 ≤ 1 周，用于验证 skill 覆盖是否完整），不能是终态。终态必须是"AI 只从 skill 获取规则"。

### 3.3 删除原文件必须全员同步（组织协调，不是技术问题）

删除一个**团队共享的**规则文件，会让其他人下次 pull 时丢失该文件。因此：

- **必须一次性、全员同步执行**，并提前告知
- **不能**由一个人悄悄删（其他人会静默失去规则，且不知道为什么 AI 行为变了）
- 建议流程：公示 → 全员确认 skill 已同步（`sfx sync` 完成）→ 统一删除 → 各人 `sfx conv sync` 重建约定文件

> 这一点与 **FR-48 路径 c（`--takeover`）的风险同源**：两者的本质都是"动了一个别人也在用的共享文件"。FR-48 的二次确认提示应当复用本节的措辞。

## 4. 团队其他成员如何同步过渡（分阶段剧本）

| 阶段 | 谁 | 做什么 | 依赖 |
| --- | --- | --- | --- |
| **S0 试点** | 规范维护者 1 人 | 本地完成 §1 盘点 + §2 拆分，验证 skill 覆盖完整 | **M1**（单机能力） |
| **S1 上传** | 维护者 | 把拆分好的 skill 提交到团队服务端 | **M2**（FR-29 / FR-31） |
| **S2 全员拉取** | 全体成员 | `sfx sync` 拉取 skill → 各自 `sfx conv sync` 生成本机约定文件 | **M2** |
| **S3 并行验证** | 全体成员 | 原文件与 skill **短暂共存**（≤1 周），成员反馈 skill 是否有遗漏 | — |
| **S4 统一处置** | 负责人 + 全员 | 按 §3.3 一次性处理原文件（删除或降级为 `docs/`） | — |
| **S5 回归** | 全体 | 各人重新 `sfx conv sync`，确认约定文件中只剩 SkillForge 块 | — |

> **关键排期结论**：**团队级迁移依赖 M2 服务端**。若规范文件原本是团队共享资产，转成 skill 后仍需团队共享 → 就必须有服务端。
> **M1 阶段只能完成个人试点（S0）**，无法完成团队迁移。这一点应在向用户承诺时说清楚，避免误以为 M1 就能全组切换。

## 5. 迁移验收清单

- [ ] 原文件中的**每一条规则**都能在某个 skill 中找到对应（无遗漏）
- [ ] 原文件中的**非规则内容**已剥离到 README / `docs/`（未混入 skill）
- [ ] 每个 skill 的 `summary` 与 `triggers` 已补齐（非自动生成的占位值）
- [ ] 执行 `sfx conv sync` 后，仓库**无任何新增 Git diff**（FR-46 / FR-48 核心验收）
- [ ] `sfx doctor` 无 CRITICAL 告警，候选文件名无冲突
- [ ] 每个成员在 Metis 中实测：提一个真实任务，能命中预期 skill
- [ ] 原文件已按 §3.3 **全员同步**处置，无成员处于"半切换"状态

## 6. ⚠ 迁移暴露的六个 FR-48 未覆盖场景（**需回到 PRD / 架构确认**）

> 这是本指南最重要的产出。以下场景在真实迁移中大概率出现，但 FR-48 当前设计未处理。

| # | 场景 | 问题 | 建议处理 |
| --- | --- | --- | --- |
| **6.1** | **多文件同时存在**（`.cursorrules` + `CLAUDE.md` + `.github/copilot-instructions.md`） | FR-48 的"换名"路径若只检查一个候选，可能换到一个同样被占用的名字 | 冲突检测必须**遍历全部候选文件名**，一次给出"全部已被占用"的明确结论，而非逐个试错 |
| **6.2** | **原文件本身是团队长期维护的资产** | `--takeover` 会 `git rm --cached`，等于**摧毁一份团队资产**；二次确认只说了"其他人会丢失文件"，没说"这份内容可能没有第二份副本" | 路径 c 应增加**前置步骤**：建议先 `sfx import` 把原文件转成 skill 并上传团队，**再**允许接管 |
| **6.3** | **候选文件不在项目根目录**（如 `.github/copilot-instructions.md`） | 若检测逻辑只扫根目录文件名，会漏掉这类文件 → 静默接管 | 候选清单必须包含**带子目录的路径**，不只是文件名 |
| **6.4** | **monorepo / 多子项目** | 一个仓库下多个子项目各自有规则文件，"项目根"的定义不唯一 | 需明确 FR-48 的检测单位是"仓库根"还是"当前项目根"（与架构 §12.5 项目定位算法联动） |
| **6.5** | **转换后 skill 的存放位置** | 若 skill 落在项目内 `.skills/` 会被 Git 跟踪——但按 §5 的验收"不得产生 Git diff"，两者矛盾 | 需明确：**团队 skill 走服务端（不落项目内）；本地 skill 落在项目外的全局目录**。迁移指南必须指明 skill 落在哪 |
| **6.6** | **worktree / submodule 场景** | `.git` 可能是**文件**而非目录，`git ls-files` 与 `.git/info/exclude` 的行为需确认 | 架构侧须给出明确退化行为，**不得留"待定"**（已在 PRD §11 下一步中列为待架构侧项） |
